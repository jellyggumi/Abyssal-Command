**질문**: 넉백·실제 비행 투사체·유닛 충돌 분리 같은 **시뮬레이션 레이어 물리**를,

## 1. 기존 코드가 이미 답을 갖고 있었다 (핵심 발견)

이 시뮬레이션은 **이미 무리수 부동소수점 연산을 쓰고 있다**. 없는 게 아니었다:

| 연산 | 사용처 | 결과가 상태로 가는가 |
|---|---|---|
| `Math.hypot` | `defense-run-simulation.js:1059` (적 이동), `:1469` (커맨더 라우팅) | 예 — 위치 갱신에 직접 투입 |
| `Math.sqrt` | `:1100` (압박 타깃 거리) | 아니오 — 비교에만 사용 |

그럼에도 digest가 안정적인 이유는 **모든 상태 기록부가 정수로 양자화되기 때문**이다.
위치를 쓰는 8개 지점 전부가 예외 없이 이 규율을 지킨다([OBSERVED] grep으로 비양자화
기록 **0건**):

```js
// defense-run-simulation.js:1062 — 무리수 중간값, 정수 기록
enemy.x = clamp(Math.round(enemy.x + dx / distance * movement), 0, ARENA.width);
// :1479 — Math.trunc 계열
run.commander.x = clamp(run.commander.x + Math.trunc(vector.x * commanderSpeed / 1000 / TICK_RATE), 0, ARENA.width);
// :1612 — 정수 + 정수 오프셋
companion.x = clamp(run.commander.x + offset.x, 0, ARENA.width);
```

즉 이 프로젝트의 결정론 전략은 "부동소수점을 쓰지 않는다"가 아니라
**"부동소수점은 중간값으로만 쓰고, 상태에 쓰기 직전 정수로 양자화한다"**이다.
물리 도입 여부는 이 규율을 물리 연산에도 확장할 수 있는가의 문제로 환원된다.

## 2. 실측 — 양자화가 실제로 발산을 흡수하는가

세 가지를 측정했다. 전부 재현 가능한 프로브(`/tmp/spike-*.mjs`, 본 문서에 코드 요지 수록).

**측정 1 — 수식 순서 민감도** (수학적으로 동일하나 평가 순서가 다른 두 넉백 구현 비교,
20,000 케이스):

| 조건 | 발산 건수 |
|---|---|
| 원시 부동소수점 (`p.x + (dx/d)*force` vs `p.x + force*(dx/d)`) | **57 / 20,000 (0.285%)** |
| 동일 값을 `Math.round()` 통과 후 비교 | **0 / 20,000** |

**측정 2 — 엔진 간 `hypot` 차이 내성** (진짜 위험. `Math.hypot`/`sin`/`cos`는 명세상
비트 동일이 보장되지 않아 엔진/버전 간 last-ULP 차이가 가능. 200,000 케이스):

| 지표 | 값 |
|---|---|
| 반올림 `.5` 경계까지 최단 접근 거리 | **6.841e-7** |
| 경계 1e-9 이내 표본 | **0** |
| `hypot` 결과에 4-ULP 섭동을 가했을 때 반올림 뒤집힘 | **0 / 200,000** |

해당 크기(≈1e3)에서 double의 1 ULP는 ≈1e-13이므로, 경계 마진(≈1e-6)은 ULP보다
**약 7자릿수 크다**. 엔진 간 마지막 비트 차이가 양자화 결과를 뒤집을 여지가 실질적으로 없다.

**측정 3 — 틱 간 오차 누적** (가장 강한 논거. 200 시행 × 600틱 = 120,000 틱스텝):

| 조건 | 최초 발산 틱 |
|---|---|
| 양자화 (매 틱 정수 기록) | **발산 없음 (-1)** |
| 비양자화 (부동소수점 상태 유지) | **틱 95에서 발산** |

이것이 결정적이다. **매 틱이 정수를 기록하므로 오차가 누적될 수 없다** — 각 틱은 정확한
정수에서 새로 시작하고, 그 틱의 부동소수점 오차는 기록 시점에 0으로 리셋된다. 반면
부동소수점 상태를 유지하면 95틱(=1.6초) 만에 궤적이 갈라진다.

## 3. GO 조건 — 물리 도입 시 강제할 규율

1. **모든 상태 기록은 정수 양자화**. 물리가 계산한 위치·속도·충격량이 `run.*`에 저장될 때
   반드시 `Math.round`/`Math.trunc`를 통과해야 한다. 기존 8개 위치 기록부와 동일한 규율.
2. **부동소수점 상태를 틱 간에 이월하지 않는다**. 속도/가속도를 유지해야 하는 물리라면
   그 필드 자체도 정수 양자화 대상이다(예: 밀리유닛/틱 정수). 측정 3이 보여주듯 이월된
   부동소수점은 1.6초 만에 발산한다.
3. **외부 물리엔진(Rapier/cannon-es/ammo.js)은 이 규율을 만족시킬 수 없으므로 부적합**.
   이들은 내부 solver 상태를 부동소수점으로 틱 간 이월하며, 그 내부 표현에 우리가 양자화를
   삽입할 수 없다. 도입한다면 **이 코드베이스 규율에 맞춘 자체 구현**이어야 한다.
4. **`Math.sin`/`cos`/`atan2` 신규 도입 시 재측정**. 본 스파이크는 `hypot`/`sqrt`만
   측정했다. 삼각함수는 엔진 간 편차가 더 클 수 있으므로 §2 측정 2를 해당 함수로 반복한 뒤
   도입한다.

## 4. 측정하지 않은 것 (한계 명시)

- **다른 JS 엔진에서 실제로 실행해 대조하지 않았다.** 4-ULP 섭동은 엔진 차이의 *대리
  지표*이지 실측이 아니다. 실제 위험이 4 ULP를 넘는다면 결론이 달라질 수 있다 — 다만
  마진이 7자릿수라 그럴 개연성은 낮다.
- **적대적 입력이 아닌 구조적 격자 표본**이다. 반올림 경계에 의도적으로 근접하도록 설계된
  입력이라면 경계 마진이 좁아질 수 있다. 물리 구현 시 실제 값 분포로 §2를 재측정할 것.
- **불가능성 증명이 아니라 실용적 위험 한계 설정**이다.

## 5. 권고

**시뮬레이션 물리는 도입 가능하다** — 단 외부 엔진이 아니라 §3 규율을 따르는 자체 구현으로,
그리고 도입 시 측정 3(장기 틱 발산 테스트)을 영구 회귀 테스트로 함께 넣는 조건이다.
