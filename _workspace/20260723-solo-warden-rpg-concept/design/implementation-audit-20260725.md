# Implementation Audit — 2026-07-25

Ground-truth audit of the CURRENT live `app.js`/`styles.css`/`battle-realtime-three.js`/`defense-run-simulation.js` code, run against `design/UNIFIED-GDD.md` and `design/core-loop.md`. All claims below are [OBSERVED] from reading the actual code and/or a real browser session against a local static server (`python3 -m http.server`, `index.html` served unmodified), unless marked [INFERENCE]. Screenshots are real captures from that session, not mockups.

**Headline finding**: the GDD (`UNIFIED-GDD.md`, committed 2026-07-24 03:47) describes a Stage-1-concept state that the *code itself has since moved past* — most visibly, GDD §5.1 says the project adopted a Blender-baked cel-shade Canvas2D atlas with a fixed bird's-eye camera, but the shipped renderer (`battle-realtime-three.js`) is a real `THREE.WebGLRenderer` scene with PBR (`MeshStandardMaterial`) GLB models and a claimed-but-unimplemented free-orbit camera. This isn't a documentation bug in the traditional sense — a later decision record (`production/decision-log.md` D17, dated after the GDD) and `production/presentation-spec.md` (updated same day) both formally superseded GDD §5.1/§5.2. **The GDD itself is stale relative to the project's own more-current decision trail**, and neither fully matches the code, which has its own internal gap (orbit/zoom are called but never implemented). Treat this report, not the GDD, as ground truth for "what the game currently does."

## 1. Current CSS/layout system

**File**: `styles.css` (419 lines, read in full).

- **Layout technique**: predominantly CSS Grid for panel/card layouts (`display: grid` — `.defense-grid` L15, `.ops-grid` L140, `.loadout-slots`/`.companion-grid`/`.reward-grid` L164, `.growth-stat-grid` L201, `.growth-formation-row` L212), with Flexbox for one-dimensional toolbars/rows (`.storage-row` L18, `.hud-actions` L43, `.command-tab-bar` L254, `.command-segment-bar` L258). No CSS custom-layout systems (subgrid, container queries) are used.
- **Panel/HUD structure**: two co-existing shells.
  1. **Lobby** (`.defense-lobby`, L10): a single scrolling document — `<header class="command-header">` (L96/533) → idle-return banner (L537) → `<nav class="command-tab-bar">` (5 tabs, L538) → `<div class="command-tab-panel">` holding exactly one of 5 tab bodies at a time (L539/525-531 in `app.js`) → a persistent "기록 관리" (record management) `<details>` footer (L540). Two of the 5 tabs (성장/growth, 동료/companions) have a nested sub-nav (`.command-segment-bar`, L258) — e.g. growth's 스탯/스킬트리/특성 (stats/skill-tree/traits) sub-tabs.
  2. **Battle** (`#defense-battle-surface`, L22): a `position: fixed` full-viewport shell holding `#defense-canvas` (the 3D/2D render surface, L36), `#world-hud-overlay` (world-space DOM HUD, L69), and `#defense-edge-hud` (L37) — an edge-anchored, pointer-events-none-by-default overlay with two `.defense-edge` bands (`.defense-top` L39, `.defense-bottom` L40) that position `.hud-panel` cards at the physical screen edges only. No central-panel HUD exists during live combat except the pause overlay (`#defense-pause-overlay`, L269), which is explicitly gated to `userPaused===true` only.
- **Color palette (CSS custom properties)**: two coexisting token sets under `:root` (L313-355 — note: a duplicate `:root` selector, not merged into the top-level `:root` at L1). Set 1, "rc-*" semantic tokens: `--rc-cyan #80d8ff`, `--rc-purple #b992ff`, `--rc-amber #e9c46a`, `--rc-green #70d3ae` plus soft/alpha variants, `--rc-panel-glass`, `--rc-panel-border`, and 3 role-accent colors (`--rc-role-vanguard #6fa8dc`, `--rc-role-striker #e08a4a`, `--rc-role-support #6fd3c7`). Set 2, "canon-*" material tokens (L347-354, added same session as the WebGL migration per its own comment L333-346): `--canon-void-obsidian #3c2c5b`, `--canon-cold-steel #737990`, `--canon-cyan-rift #2cadd6`, `--canon-zenith-gold #ddc869`, `--canon-cinder-ember #f3592c` — measured directly from the shipped GLB materials' sRGB base colors, applied only to 4 "high-exposure decorative" surfaces (aurora backdrop, glow-ring, portrait socket, panel-glass per the code comment at L340). Base document colors (background `#050812`, text `#eef5ff`) are hardcoded at `:root` L1, not tokenized.
- **Breakpoints**: exactly one, `@media (max-width: 720px)` (L223, mobile), reducing hero/ops grids to 1 column and shrinking several HUD max-widths. No tablet/desktop-specific breakpoint exists — the layout is mobile-first with the same grid used unmodified above 720px (grid columns use `auto-fit`/`minmax()` fluid sizing rather than fixed breakpoints for wider viewports). A separate `@media (prefers-reduced-motion: reduce)` query appears twice (L89-92, L244-247, L414-419), disabling animations/transitions/scroll-behavior globally.
- **Animation/transition usage**: transitions are narrow and functional — `transition: width 120ms linear` on health-bar fills (`.integrity-meter i` L194, `.gate-panel-bar-track i` L294), `transition: transform/box-shadow/border-color 160ms ease` on `.rc-lift` card press/hover feedback (L363). Keyframe animations: `world-capture-pulse` (opacity pulse, L87), `world-damage-rise` (rising/fading damage numbers, L88), `rc-glow-spin` (rotating conic-gradient border on selected cards via `@property --rc-glow-angle`, L370-380), `rc-aurora-drift` (slow background gradient drift, L391). All are neutralized under `prefers-reduced-motion: reduce`.

## 2. Current core-loop mechanics as they actually execute in code

**File**: `defense-run-simulation.js` (1986 lines).

- **What triggers combat**: entirely automatic, deterministic 60Hz tick simulation (`TICK_RATE`, `tick()` at L1424-1655). The player has **zero direct attack input** — the commander auto-fires at the nearest in-range target every tick via the existing `fire()`/`orderedTargets()` pipeline (unchanged by the RPG layer). Player agency is limited to: (a) 9-directional movement (`OCTANT_VECTORS`, `defense-catalog.js:13-17`, consumed at `defense-run-simulation.js:1450-1452`), (b) skill-cast inputs (`castSkill()`, L639-746), and (c) lobby-only Growth/Equipment/Formation purchases. This matches GDD §2.1's "automatic combat resolution stays 100%" decision — [OBSERVED] correct.
- **Formation/stance system — the single largest design/code gap found**: the GDD (§2.2, and `core-loop.md`) specifies a 3-stance system (전열/Vanguard, 포대/Turret, 분산/Split) with distinct spatial offsets (front ±500u, turret 300u tight rear, split up to 9000u wide) and a 4-second stance-switch cooldown. **None of this exists in code.** What's actually implemented is a strictly binary `FRONT`/`BACK` **slot** system (`resolveFormation()` L200-209, `MAX_FRONT_SLOTS` from `rpg-catalog.js`, UI toggle at `app.js:394-400`/`623-633`). `FRONT` companions are eligible to be targeted by enemies and can be `DOWNED` (run-scoped, resets on next run); `BACK` companions get a +25% damage synergy bonus (`BACK_ROW_SYNERGY_DAMAGE_BONUS = 0.25`, `rpg-catalog.js:100`) when ≥1 FRONT companion is alive. Critically, **all companions share the commander's exact position every tick** — there is no distinct stance-offset positioning at all (explicit code comment, `defense-run-simulation.js:186-188`: "Companions are position-pinned to the commander every tick (no distinct stance-offset positions this cycle — deferred, see task-manifest.md)"). This deferral is independently confirmed in `production/task-manifest.md:31`. The FRONT/BACK *targeting/DOWNED/synergy/Rally mechanics* the GDD describes as consequences of stances ARE implemented and correct; only the "3-stance, spatially-offset formation" presentation layer is missing.
- **Undertow Encroachment / idle-return mechanic**: **fully implemented, matches the GDD formula exactly**, in `campaign-state.js`. `wardLevel(campaign)` (L218) = `resolvedIds.length + floor(companionCollection.length / 2)`. `settleIdleReturn()` (L221-250) computes `wardlinePressure(elapsedMs)` = `min(floor(elapsedMs / (60 * IDLE_RETURN_INTERVAL_MS)), 8)` (L220) and returns an `ENCROACHED` receipt (L241-243, forfeiting that window's idle progress, no permanent loss) when `pressure > wardLevel`, or `SETTLED` (awards progress) otherwise. This is surfaced in the lobby via `idleReturnSummary()` (`app.js:227-243`) and rendered as the `#idle-return-summary` banner (`app.js:537`, visible at the top of the lobby screenshot below). This is the one system where GDD-claimed-formula and shipped-code are byte-identical.
- **Reward/pacing cadence**: the GDD's `core-loop.md` numeric model (`vanguard-circuit` 60s±band, `formation-assault` 100s±band, "2 reward events per loop") is explicitly labeled `[TARGET]` in the source doc and is **not a literal timer or event-count constant anywhere in the code** — it's a design aspiration about emergent pacing, not a coded mechanic. What IS coded and drives actual pacing: `XP_GROWTH = [30, 55, 85, 120, 160, 205, 255, 310]` (8-stage XP thresholds, `defense-catalog.js:131`, unchanged from pre-RPG-layer baseline), the fixed `updateObjectivePhase()` sequence `gate-defense → echo-recovery → growth → occupation → extraction → boss-kill` (L1213-1219, exactly matching `core-loop.md`'s stated phase order), and `BOSS_RALLY_COOLDOWN_REDUCTION = 0.20` firing once per boss spawn when ≥1 FRONT companion is alive (`spawnBoss()` L346-352, `rpg-catalog.js:102`) — this is the GDD §4.3 "Boss Rally Window," correctly implemented. The GDD's other named skill-reversal mechanic, "Formation Surge" (결집 강화, §7.2, itself labeled `TARGET — Stage2 QA 시뮬레이션 전까지 DRAFT`), has **no code anywhere** (repo-wide grep for `formationSurge`/`결집 강화`/`formation-surge` returns zero matches) — it is a pure design draft, not deferred-but-partial like the stance system.

## 3. Camera, VFX, and HUD-to-3D coordination (`battle-realtime-three.js`, 1174 lines)

- **Camera model — claimed free-orbit, actually still a fixed follow camera; the orbit input path is dead code.** `RealtimeBattle.updateCamera(snapshot)` (L925-942) computes a `THREE.PerspectiveCamera` position as `cameraTarget + Vector3(0, WORLD_SCALE*1.05, WORLD_SCALE*1.05)` (L939) — a **hardcoded fixed elevation/azimuth offset** (functionally ~45° from horizontal, always looking from the same relative direction), lag-eased at 0.18 toward the commander's world position (L933-935) with a reduced-motion hard-snap (L936-938). This is architecturally the *same fixed-offset-follow pattern* as the legacy Canvas2D camera, just executed in 3D instead of 2D. Meanwhile, `app.js`'s pointer handlers (`onPointerMove`, L924-941) call `this.renderer?.orbit?.(dx, dy)` (L940, one-finger drag) and `this.renderer?.zoom?.(delta)` (L932, two-finger pinch) — **neither `orbit()` nor `zoom()` is defined anywhere on `RealtimeBattle` or on the Canvas2D fallback `BattleVisualizer`** (repo-wide grep confirms zero definitions). Because both calls use JS optional-chaining (`?.`), they silently no-op instead of throwing. **Empirically verified**: a scripted 200px canvas drag during a live battle session produced byte-for-byte the same camera framing before and after (screenshots `audit-06-before-drag.png`/`audit-06-after-drag.png` below) — confirming the orbit path is inert in the running app, not just in static reading. The code comments (`app.js:49-51`, `899-902`) and `production/decision-log.md` D17 / `presentation-spec.md` L19-21 all describe/claim a working "free orbit — yaw unrestricted, pitch clamped [30°,85°]" camera; this description does not match the shipped renderer.
- **VFX spawn system**: event-driven, GLB-based. `spawnVfx()` (L953-978) reacts to 5 telemetry event types mapped in `VFX_MODELS` (L155-162, e.g. presumably `SKILL_CAST`/`CRITICAL_HIT`/etc. — exact keys elided in structural summary but referenced as "5 RPG-layer telemetry events" at L150-154) by instantiating a GLB at the event's world anchor (`effectAnchor()`, L322-330) with a pooled cap of `MAX_VISUAL_EFFECTS = 24` (L13, oldest evicted at L966-970). A separate "death echo" system (`captureDeathEchoes()`/`spawnDeathEcho()`, L988-1023) plays a short-lived standalone die-animation clone at a defeated enemy's last position — the real actor is removed from the simulation immediately per contract, the echo is purely decorative. Both pools use lifetime-tick bookkeeping (`untilTick`) cleaned up in `collectFeedback()` (L1074-1096).
- **HUD-to-3D coordination**: two distinct paths. (1) *Screen-space DOM HUD* (`#defense-edge-hud`) is updated independently by `app.js`'s `render()` (L1182+) via direct `textContent`/`style.width` writes keyed to element IDs (`#battle-commander-integrity`, `#battle-integrity-fill`, etc., L1255-1270) — no coordinate math, pure data binding. (2) *World-space DOM HUD* (`#world-hud-overlay`) is computed each frame by `app.js`'s `renderWorldHud()` (L1286-1461+), which calls `this.renderer.projectStaticPoint()`/`projectEntityToScreen()` on the live `RealtimeBattle` instance to convert world/normalized coordinates into screen-space CSS `transform: translate()` values for companion nameplates, the extraction capture prompt, an offscreen-objective waypoint arrow (edge-clamped, L1300-1326), and floating damage numbers (L1450-1460, capped at 24 pooled nodes). This is the "World-space HUD (Track 3)" from the Cycle 3 retrospective — confirmed working in the combat screenshot below (objective chip, integrity bars). Note the retrospective's own admission (`cycle-3-retrospective.md` L35-50): a pre-existing dead-code bug meant **the boss never had a visible mesh in any WebGL battle until this same session fixed it** — a severity worth flagging even though it's since been patched.

## 6. Other notable findings (not requested as gap-table rows, but load-bearing for a redesign)

- **`updateCamera` in `app.js` (L869-887) is a legacy screen-space pan offset used only for the DOM overlay's portrait-rotation CSS transform and the Canvas2D `BattleVisualizer` fallback path — it does not drive the WebGL camera at all.** `RealtimeBattle.renderSnapshot()` (`battle-realtime-three.js:1098-1115`) computes its own camera internally from the raw snapshot (L1110, `this.updateCamera(snapshot)`) and never reads `frame.camera` (the value `app.js` passes at L1225). Any redesign touching camera behavior must change `battle-realtime-three.js`, not `app.js`'s `updateCamera`.
- **GDD line-number citations are stale.** E.g. `UNIFIED-GDD.md:251` cites "camera tracking hard-cut pattern [OBSERVED] `app.js:534-551`" — the actual `updateCamera()` method is now at `app.js:869-887`. The file has grown/shifted since the citation was written; treat all GDD line citations as approximate, re-verify before use.
- **`campaign-state.js:26`, not `:20`, defines `MAX_LOADOUT_SIZE = 3`** — `UNIFIED-GDD.md:109` cites line 20; off by 6 lines, same staleness pattern as above.
- **`task-manifest.md` (Cycle 1) is stale relative to the current code** — it lists the 5-tab UI shell and the WebGL/camera-orbit work as "deferred, follow-up," but both landed in later Cycle-3 commits (`c31cae7`, `9855a78`, `9a60a49`) that are recorded in `task-manifest-cycle2.md`'s absence and only in `retrospectives/cycle-3-retrospective.md` and `decision-log.md` D17 — not in any updated task-manifest. A redesign session should treat `decision-log.md` (chronological) and direct code reading as more current than `task-manifest.md`.
