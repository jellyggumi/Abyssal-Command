# Review Checkpoint 1 — 직관성/밸런스/재미 평가 (2026-07-25)

run-id: `20260723-solo-warden-rpg-concept` · director: game-production-director
범위: Implementation 단계 완료 직후 첫 체크포인트 — 3-스탠스 편성 시스템(코어루프), 궤도 카메라(조작감),
UI 재설계(정보구조) 3개 축을 실측 데이터 기반으로 평가한다. Stage 2 정밀 밸런싱 이전의 **개념 검증
체크포인트**이므로, 수치 최적화가 아니라 "설계가 실제로 작동하는가/의도한 대로 차별화되는가"를 검증한다.

## 방법론

`defense-run-simulation.js`를 직접 구동해 결정론적 시뮬레이션으로 실측 — 추측이 아니라 실제 게임
상태 전이를 관찰했다. 스테이지 3(echo-throne, 중간 난이도)과 스테이지 7(starless-canal, 고난이도)
양쪽에서 각 스탠스당 5개 시드로 트라이얼 실행.

## 1. 밸런스 — 3-스탠스 실측 차별화

### 1.1 게이트/커맨더 보호 (스테이지 3, 5시드 평균)

| 스탠스 | 게이트 내구 손실 | 커맨더 잔여 내구 |
|---|---:|---:|
| 전열(VANGUARD) | 36 | 1024 |
| 포대(TURRET) | 58 | 971 |
| 분산(SPLIT) | 47 | 1005 |

**해석**: 전열이 최고의 방어(적이 커맨더보다 동료와 먼저 교전), 포대가 최악(FRONT 0, 스크리닝 없음) —
설계 의도(§2.2 "동료가 커맨더보다 먼저 접근로 진입, 조기 교전")와 정확히 일치.

### 1.2 화력 출력 (스테이지 7, 5시드 평균, 2500틱 window)

| 스탠스 | 동료 총 피해량 |
|---|---:|
| 전열 | 65,724 |
| 포대 | 60,228 |
| 분산 | **67,635** (최고) |

### 1.3 동료 피격량 — 포대의 실제 정체성 (스테이지 7, 5시드 평균)

| 스탠스 | 동료가 받은 피해 총량 |
|---|---:|
| 전열 | 761 |
| 포대 | **0** |
| 분산 | 104 |

**🚩 발견 — GDD 서술과 실측 불일치**: `UNIFIED-GDD.md:82`가 포대(Turret)의 "주 효과"를 "재배치 지연
최소, **지속 화력 최대**"로 서술하지만, 실측 결과 포대는 3개 스탠스 중 **화력이 가장 낮다**(60,228 <
65,724 < 67,635) — 이는 포대의 파생 FRONT수 0이 `BACK_ROW_SYNERGY_DAMAGE_BONUS`(FRONT≥1 생존 시 BACK
+25%)를 구조적으로 받을 수 없기 때문이다(`rpg-catalog.js` `BACK_ROW_SYNERGY_DAMAGE_BONUS`,
`defense-run-simulation.js` 시너지 게이트 로직). `core-loop-redesign-20260725.md` §3.4가 이미 발견한
"포대-Boss Rally Window 상호배제"와 **동일한 근본 원인**(FRONT≥1 게이트)의 **두 번째 사례**다 — 후열
시너지 역시 FRONT≥1을 요구해 포대만 배제된다.

반면 포대는 동료 피격량이 **정확히 0**이다 — FRONT 슬롯 동료만 적의 타겟팅 대상이 되므로
(`playerSideTarget`), 포대의 진짜 정체성은 "화력 극대화"가 아니라 **"동료 완전 무피해(제로 리스크)"**다.
이는 여전히 유효하고 흥미로운 전술적 정체성이지만, GDD 서술이 실제로 관찰되는 트레이드오프를 잘못
설명하고 있다.

**권고**: `UNIFIED-GDD.md:82`의 "지속 화력 최대"를 "동료 무피해(제로 리스크), Boss Rally/후열시너지
양쪽 다 미적용"으로 정정 — 수치 리밸런싱(포대에 화력 보상 부여 등)이 아니라 **문서 정정**을 1차
권고한다. 수치적 보상 여부는 Stage 2 밸런스시트 소관(이미 `core-loop-redesign-20260725.md` §5 디렉터
노트가 3가지 해법 옵션을 남겨둠 — 이번 발견이 그 옵션 결정에 추가 근거를 제공).

## 2. 직관성 — 조작 모델 검증

- **탭-사이클 단일 버튼**(코드 리뷰로 확인, `app.js` `renderControls`): 3개 옵션을 순환하는 단일 버튼은
  Kingshot/Whiteout 리서치 근거(드래그 아닌 탭 기반)와 정합. 방사형 쿨다운 링 + 초 단위 텍스트 이중
  피드백으로 "왜 반응이 없는가" 혼란 방지.
- **궤도 카메라와 이동 입력 분리**: `ControlFeelDesign`이 이미 3중 방어선(별개 DOM 리스너, 포인터캡처,
  기하학적 여유 마진)을 코드 인용으로 검증 완료 — 재확인 불필요.
- **결정 밀도**: 4초 쿨다운 기준 스테이지 3 완주(40.9초)에 최대 10회, 스테이지 7(49.8초)에 최대 12회
  전환 가능 — `core-loop-redesign-20260725.md`가 의도한 "상시 가용한 자유 재전환"이 실제로 스테이지
  1회 완주 동안 여러 번 유의미하게 발동 가능한 빈도임을 확인. 1회성 사전 선택이 아니라 진짜 실시간
  전술 레이어로 기능한다.

## 3. 재미(전술적 깊이) — 트레이드오프 공간 검증

3개 스탠스가 서로 다른 축에서 우위를 갖는 것을 확인 — 단일 지배 전략이 존재하지 않는다:
- **전열**: 최고 방어(게이트/커맨더 보호) — 탱킹 우선
- **분산**: 최고 화력 — 딜 우선, 방어는 중간
- **포대**: 완전 무피해(0 동료 피격) — 안정성 우선, 화력은 최저, 랠리/시너지 보너스 전부 미적용

이는 진짜 트레이드오프(모든 축에서 우월한 스탠스 없음)로, "어떤 상황에 어떤 스탠스를 쓸 것인가"라는
실시간 판단 여지를 만든다 — QA 리스크등록부 R2가 우려한 "단일 지배 전략" 붕괴 패턴이 스탠스 레벨에서는
관측되지 않는다(단, R2의 진짜 우려인 "역할(role) 다양성"은 `core-loop-redesign-20260725.md` §3.4가
이미 별도 검증 필요로 표시 — 이 체크포인트는 스탠스 자체의 차별화만 확인, 역할 다양성은 범위 밖).

전부 코드 직접 확인 + 해당 테스트 그린으로 검증 완료.

## 결론 및 다음 단계

**PASS, 조건부 문서 정정 필요**: 3-스탠스 시스템은 직관적이고(탭-사이클, 명확한 피드백), 밸런스
측면에서 실제로 차별화되며(단일 지배 전략 없음), 전술적 깊이를 제공한다(4초 쿨다운이 스테이지당
10-12회 유의미한 재전환을 허용). 유일한 이슈는 **GDD의 포대 서술 오류**(화력이 아니라 무피해가 진짜
효과) — 코드나 수치를 바꾸는 것이 아니라 문서를 실제 동작에 맞게 정정하는 것으로 해소 가능.

**Review Checkpoint 2로 이월**: 이 체크포인트는 스탠스 시스템에 집중했다 — 궤도 카메라의 실제 시각적
느낌(각도별 조명/안개 체감)과 UI 전체 정보 밀도의 실제 체감은 스크린샷 기반 시각 검증이 필요하며,
다음 체크포인트에서 다룬다.
