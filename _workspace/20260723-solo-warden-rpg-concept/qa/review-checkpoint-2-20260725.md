## 방법론

코드 리뷰만으로는 "존재한다"와 "실제로 작동한다"를 구분할 수 없다는 것이 이 프로젝트의 반복된
교훈(D19/D20 다수 발견) — 이번 체크포인트는 실제 브라우저에서 클릭/드래그/스크린샷으로 검증했다.

## 1. 발견 — 실제 버그 1건 (코드 리뷰로는 안 잡히는 통합 결함)

### 1.1 카메라 힌트 토스트가 생성 직후 1.5ms만에 자동 제거됨

**증상**: `maybeShowCameraHint()`가 토스트를 정확히 생성하지만(`Element.prototype.append` 계측으로
확인), 같은 렌더 패스 안에서 즉시 `remove()`되어 화면에 전혀 보이지 않음.

**근본 원인**: `renderControls()`의 성장 선택 카드 정리 로직(구 `app.js:1553`)이
`root.querySelector(".edge-card:not(.defense-result)")`로 "성장 카드가 아닌 다른 edge-card"를
찾고 있었다 — 이 셀렉터는 성장 카드가 이 프로젝트 유일의 비-result edge-card이던 시절에 작성됐다.
이번 사이클이 신규 도입한 카메라 힌트 토스트(`.edge-card.defense-toast.defense-toast-camera-hint`)도
같은 `.edge-card` 클래스를 쓰므로 이 셀렉터에 걸렸고, `snapshot.growthOffer`가 없는 매 프레임마다
"성장 카드 없음 → 찾은 카드 제거"(`else if (card) card.remove()`) 로직이 토스트를 성장 카드로
오인해 즉시 삭제했다.

**판정**: `#defense-growth-offer` 고유 ID 기반 조회로 교체(`app.js`, 셀렉터 범위를 클래스에서
ID로 좁힘) — 이 ID는 생성 시점에만 부여되고 다른 곳에서 조회되지 않아 안전하게 교체 가능함을
확인 후 적용. 재검증: 토스트가 정상 표시되고(스크린샷 확인, 정확한 디자인 문서 카피/픽토그램
렌더링), 첫 궤도 제스처 시 정상 해제됨을 확인.

**교훈**: 5개 병렬 구현 레인이 각자 파일 경계를 정확히 지켰음에도(`CameraRenderLane`/
`FormationStanceLane`/`BattleUILane` 전부 자기 파일만 수정), **같은 CSS 클래스 이름공간을 공유하는
셀렉터 하나가 사전 조율 없이 두 레인의 산출물을 충돌시켰다** — 이는 코드 리뷰(diff 확인)로는 발견
불가능했고 실제 브라우저 실행으로만 잡을 수 있었다. `report_tool_issue` 성격의 발견이 아니라
this-session의 실제 통합 결함.

## 3. 환경 이슈 — 서비스워커 캐시 (D19 재확인, 신규 아님)

이번 검증 중 두 차례 서비스워커가 이전 세션의 캐시된 `app.js`/`defense-run-simulation.js`를 계속
서빙해 신규 코드가 반영되지 않는 것처럼 보이는 함정에 걸렸다 — `decision-log.md` D19가 이미 정확히
동일한 함정("서비스워커가 리깅 이전 캐시된 GLB를 계속 서빙")을 기록해 두었다. 이번 세션 QA 절차에도
동일 교훈 적용: **로컬 검증 전 항상 `navigator.serviceWorker.getRegistrations()` + `caches.keys()`로
잔존 캐시를 확인/삭제할 것.** 신규 발견이 아니라 기존 교훈의 재확인이므로 결정 기록에 신규 항목을
추가하지 않는다.

토스트 즉시 삭제)는 즉시 수정 및 재검증 완료 — 코드 리뷰만으로는 발견 불가능했던 크로스-레인 셀렉터
충돌이었다는 점에서 이 체크포인트가 실제로 가치를 제공한 사례.

**남은 리스크**: 적 네임플레이트 CSS 클래스(`world-hud-nameplate--enemy`)는 여전히 준비된 상태로만
