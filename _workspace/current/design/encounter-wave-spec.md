## 1. 페이즈 비트시트

각 페이즈는 **하나의 새 압박원**만 추가한다. 압박원을 겹쳐 쌓지 않는다.

### 1.0 `DESCENT` — 강하·정찰 (1800 tick / 30 s, 시간 상한)

| 항목 | 내용 |
|---|---|
| 목표 | 조작 확인, 맵 판독, 첫 접촉 성립 |
| 공간 | 스폰 `arena` 셀 1개 (8000 × 6000) |
| 적 역할 | `rusher` 단독 |
| 스폰 | tick 300 / 900 / 1500에 각 3마리 |
| 위험 요소 | 없음 |
| 진입 자원 | 대시 충전 2, 스킬 6칸 전부 쿨다운 0 |
| 출구 | 인접 `transit` 셀로 자동 개방 |
| 실패 복구 | 해당 없음 — 사망 불가 밀도 |
| 보상 | Echo Shard 3 |
| **새 압박원** | 없음 (기준선) |

`rusher`만 쓰는 이유: 콤보 3타(§`action-combat-spec.md` 4.4)가 `rusher` 3000 HP를 정확히
1체인에 처치한다. 플레이어가 콤보 완주 감각을 배우는 유일한 안전 구간이다.

### 1.1 `SKIRMISH` — 산개 교전 (4500 tick / 75 s, 시간 상한)

| 항목 | 내용 |
|---|---|
| 목표 | 콤보 학습 완료, 첫 성장 선택 |
| 공간 | `arena` 2개 + `transit` 1개 |
| 적 역할 | `rusher`, `flanker` (신규), `ranged` (tick 2700~) |
| 스폰 | 180 tick 간격, 배치당 4–6 |
| 위험 요소 | 정적 hazard 장판 1개 (셀당) |
| 진입 자원 | `DESCENT` 이월분 포함 |
| 출구 | `SURGE` 셀로 연결 |
| 실패 복구 | 지휘관 30% 이하 시 `shrine` 셀 개방 |
| 보상 | Echo Shard 8, 성장 제안 1회 (tick 2250) |
| **새 압박원** | 측면 접근 (`flanker`) |

### 1.2 `SURGE` — 밀집 웨이브 (4500 tick / 75 s, 시간 상한)

| 항목 | 내용 |
|---|---|
| 목표 | 광역기 필요성 체감 |
| 공간 | `arena` 1개 (가장 넓은 셀) |
| 적 역할 | 4종 전부 + `guardian` 최초 등장 |
| 스폰 | 120 tick 간격, 배치당 8–12 |
| 위험 요소 | 이동 hazard 1개 |
| 진입 자원 | 성장 1회 반영됨 |
| 출구 | `MIDBOSS` 셀 |
| 실패 복구 | `shrine` 1회 (지휘관 40% 이하) |
| 보상 | Echo Shard 14, 성장 제안 1회 (tick 3600) |
| **새 압박원** | 동시 다수 (상한 34) |

`SURGE`의 미처치 잔존은 `MIDBOSS`로 이월된다(`master-numeric-contract.md#2.1`). 이것이
"보스전에 잡몹이 섞이는" 상황을 만드는 정상 경로다.

### 1.6 페이즈 전이 이월 정책 (`CARRYOVER`)

**동시 상한은 총 생존 개체 상한이다.** 스폰 허가량이 아니다 —
`master-numeric-contract.md#9`의 성능 예산(동시 액터 ≤60)이 이 해석에 의존하므로
재해석할 수 없다.

문제: `BIGWAVE`(상한 60)에서 `FINALE`(상한 8)로 전이할 때 이월 생존이 상한을 초과할 수
있다. 명목 이월 25는 **기대값이지 최대값이 아니다.** 시뮬레이션 결과:

| `BIGWAVE` 처치율 | 종료 생존 | 미투입 백로그 | 합계 |
|---|---|---|---|
| 기대치 100% | 25 | 0 | 25 |
| 기대치 50% | 58 | 93 | 151 |
| **0% (무처치)** | **60** | **217** | **277** |

따라서 명시적 전이 정책이 필요하다.

#### 전이 규칙 (모든 페이즈 경계 공통)

| 단계 | 규칙 |
|---|---|
| 1 | 이전 페이즈의 **미투입 백로그는 폐기**한다. 월드에 존재한 적이 없으므로 이월 대상이 아니다. |
| 2 | 생존 **개체**를 id 오름차순으로 정렬해 앞에서 `CARRYOVER_QUEUE_MAX = 16`까지 이월 템플릿으로 뜬다. |
| 3 | **이전 페이즈 개체를 전부 월드에서 제거한다.** 이월분도 제거 대상이다 — 재투입은 신규 개체로 이뤄진다. |
| 4 | 초과분은 **보스 피해 부채**로 환산한다: 1체당 `+2%`, 상한 `+40%`. |
| 5 | `aliveCount = 0`으로 리셋하고 보스를 스폰한다(슬롯 1 점유). |
| 6 | 이월 템플릿을 `backlog`에 적재하고 §4.2.1 공통 규칙으로 투입한다. |

```
CARRYOVER_QUEUE_MAX = 16
DEBT_PER_EXCESS     = 0.02   // 보스 피해량 배수
DEBT_CAP            = 0.40

// --- 1. 미투입 대기열 폐기 -------------------------------------------------
spawnQueue = []                                   // 이전 페이즈 대기 템플릿은 버린다
// --- 2. 이월 템플릿 선정 (결정론: id 오름차순) -----------------------------
survivors = world.enemies
              .filter(e => e.class !== "boss" && e.hp > 0)
              .sort((a, b) => a.id.localeCompare(b.id))     // 안정 정렬
templates = survivors.slice(0, CARRYOVER_QUEUE_MAX)
              .map(e => ({ archetype: e.archetype, hp: e.hp }))  // 누적 피해 보존
excess    = survivors.length - templates.length

// --- 3. 이전 페이즈 개체 전면 제거 -----------------------------------------
for (const e of world.enemies) world.despawn(e.id)   // 이월분 포함, 예외 없음
world.enemies = []
aliveCount    = 0
// 제거는 처치가 아니다: ENEMY_DEFEATED 미방출, XP/Echo Shard/보상 트리거 없음.
// 관측용으로 PHASE_CARRYOVER_PURGED{removed, carried, excess}만 방출한다.

// --- 4. 초과분 → 보스 부채 -------------------------------------------------
bossDamageDebt = min(excess * DEBT_PER_EXCESS, DEBT_CAP)

// --- 5. 보스 스폰 ----------------------------------------------------------
spawnBoss({ damageMultiplier: 1 + bossDamageDebt })   // aliveCount = 1

// --- 6. 이월 템플릿을 대기열로 적재 ----------------------------------------
spawnQueue = templates   // EnemyTemplate[] — 신규 entityId로 재생성되어 투입된다
// 이후 admitted/alive는 §4.2.1 공통 규칙이 소유
```

**중복 불가 보장:** 3단계가 이월분을 포함해 **모든** 이전 개체를 제거하므로, 6단계에서
투입되는 개체는 전부 신규 `entityId`를 받는다. "살아 있는 원본 + 대기열 사본"이 동시에
존재하는 상태는 만들어질 수 없다.

**누적 피해 보존:** 템플릿이 `hp`를 함께 뜨므로 플레이어가 넣은 칩 데미지는 사라지지
않는다. 반쯤 깎아둔 `guardian`은 반쯤 깎인 채로 추격해 들어온다.

**제거는 처치가 아니다:** `ENEMY_DEFEATED`를 방출하지 않으며 XP·Echo Shard·보상 트리거도
작동하지 않는다. 페이즈 전이를 반복해 재화를 파밍하는 경로를 막는다.

#### 검산 (시뮬레이션)

| 진입 케이스 (생존/백로그) | 폐기 백로그 | 제거 개체 | 이월 템플릿 | 초과 | 보스 부채 | 보스 스폰 | 대기열 투입 | **진입 생존** | 잔여 대기 |
|---|---|---|---|---|---|---|---|---|---|
| 명목 (25/0) | 0 | 25 | 16 | 9 | +18% | 1 | 7 | **8** | 9 |
| 절반 (58/93) | 93 | 58 | 16 | 42 | +40% (상한) | 1 | 7 | **8** | 9 |
| 무처치 (60/217) | 217 | 60 | 16 | 44 | +40% (상한) | 1 | 7 | **8** | 9 |
| 완전 소탕 (0/0) | 0 | 0 | 0 | 0 | 0% | 1 | 0 | **1** | 0 |
| `MIDBOSS` 전이 (30/0, 상한 12) | 0 | 30 | 16 | 14 | +28% | 1 | 11 | **12** | 5 |

**불변식:**

1. 모든 케이스에서 `진입 생존 ≤ 해당 페이즈 상한`. 성능 예산이 보존된다.
2. `제거 개체 = 이전 생존 전량` — 이월분 포함. 잔존 원본 0.
3. `보스 스폰 + 대기열 투입 = 진입 생존` — 신규 개체만 존재하므로 중복 0.
4. `ENEMY_DEFEATED` 방출 0, 재화 지급 0.

#### 왜 이 형태인가

- **삭제처럼 보이지 않게 하는 서사:** 이월 개체는 사라지는 것이 아니라 보스 셀 입구로
  **추격해 들어온다.** 플레이어가 정리할수록 대기열이 비고, 정리하지 못하면 계속 밀려온다.
- **처벌은 실재하지만 유한하다:** 대기열 16 + 부채 40% 상한이 최악의 경우를 묶는다.
  277체가 순차 투입되는 무한 보스전은 발생하지 않는다.
- **부채가 HP가 아니라 피해량인 이유:** 보스 HP를 늘리면 전투가 길어져
  `STAGE_HARD_CEILING_TICKS`를 압박한다. 피해량을 늘리면 **전투가 짧아지고 위험해진다** —
  처벌의 방향이 시간이 아니라 긴장이다.
- `MIDBOSS` 전이(`SURGE` 상한 34 → 12)에도 같은 규칙을 적용한다.

`freeSlots`는 `max(0, cap − aliveCount)`로 클램프한다(§4.2.1).

## 2. 적 역할 분화

기존 4종(`defense-catalog.js#ENEMIES` `[OBSERVED]`)이 새 전투 동사 아래에서 각각
**다른 대응**을 강제하는지 검증한다.

| 적 | HP | 속도 | 의도된 대응 동사 | 간격 | 무시하면 |
|---|---|---|---|---|---|
| `rusher` | 3000 | 3000 | `LIGHT` 풀 체인 | 근접 | 밀도 누적 → 포위 |
| `flanker` | 3600 | 3300 | `LIGHT_3` 360° 피니셔 | 측후방 | 등 뒤 지속 피해 |
| `guardian` | 9000 | 1700 | `HEAVY` 경직 → 콤보 | 중거리 | 광역기 흡수, 진형 고착 |
| `ranged` | 2800 | 2000 | `DASH` 접근 → 즉살 | 원거리 6000 | 회피 중 누적 피해 |

**분화 성립 검증:**

- `rusher`는 정면 밀도 → 부채꼴 120°로 충분.
- `flanker`는 `policyId: "flank"` `[OBSERVED]`로 측후방을 잡는다. 부채꼴로는 못 잡고
  **360° 피니셔가 유일한 답**이다. 대응 차별 성립.
- `guardian` 9000 HP는 풀 체인 3510으로 3회(180 tick)가 필요하다. `HEAVY` 경직으로 끊고
  치는 편이 빠르다. 대응 차별 성립.
- `ranged`는 사거리 6000, 근접 최대 사거리는 `HEAVY` 2600. **대시 2600 없이는 도달
  불가**다. 대응 차별 성립.

**신규 아키타입 추가하지 않는다.** 4종으로 4가지 대응이 모두 커버된다. 추가는 압박원을
겹쳐 쌓는 행위이며 §1의 "한 번에 하나" 원칙을 위반한다.

### 2.1 스테이지별 재해석

같은 4종을 스테이지 시퀀스 `n`에 따라 §7 램프로 강화한다. 시각적 변주는
`stage-world-catalog.js` 팔레트로 처리하며 **행동은 동일**하다 — 학습한 대응이 10스테이지
내내 유효해야 한다.

## 3. 웨이브 밀도 곡선

| 페이즈 | 스폰 간격 | 배치 크기 | 동시 상한 | 상한 도달 시 |
|---|---|---|---|---|
| `DESCENT` | 600 | 3 | 8 | 지연 |
| `SKIRMISH` | 180 | 4–6 | 18 | 지연 |
| `SURGE` | 120 | 8–12 | 34 | 지연 |
| `MIDBOSS` | 600 | 3 | 12 | 지연 |
| `BIGWAVE` | 45 | **18 → 4** (§4.2.2 구간별) | 60 | 지연 |
| `FINALE` | 패턴 연동 | — | 8 | 지연 |

`BIGWAVE`는 단일 배치 크기를 쓰지 않는다. 급증 구간 18로 상한까지 채운 뒤 보충 구간 4로
전환한다. 이유와 검산은 §4.2.2에 있다.

**지연 규칙:** 동시 상한에 도달하면 스폰을 **연기**한다. 드롭하지 않는다. 연기된 배치는
슬롯이 비는 즉시 다음 스폰 tick에 투입된다. 이것이 성능 안전판이자 밀도 보장 장치다.

`spawnQueue`는 **정수가 아니라 `EnemyTemplate[]` 큐**다(§4.2.1). 각 원소는
`{ archetype, hp }`를 실어 이월 개체의 누적 피해를 보존한다. 신규 공급은 큐 뒤에 붙고,
투입은 큐 앞에서 꺼낸다(FIFO) — 이것이 "대기분이 신규 공급보다 먼저 투입된다"의 실행
형태다. 스냅샷에는 `spawnQueue.length`를 노출하며, 이 값이 40을 넘으면
`SPAWN_BACKLOG_SATURATED`를 방출한다 — QA가 "밀도가 아니라 처리량이 병목"임을 구별하는
신호다.

## 4. 빅웨이브 설계

### 4.1 처치율 가정 `[TARGET]`

밀도 표를 검증하려면 처치율 가정이 필요하다.

| 경로 | 처치/초 | 근거 |
|---|---|---|
| `LIGHT_3` 피니셔 (6명 밀집) | 6.0 | 9720 피해 ÷ 60 tick 취소-압축 주기, `rusher` 3000 HP 기준 |
| 실전 산개 보정 | ×0.45 | 적이 360°/2200 안에 항상 6명 있지 않음 |

주기 60 tick 출처: `master-numeric-contract.md#3.3` 취소-압축 타임라인. 취소를 쓰지 않는
플레이어는 77 tick 주기이므로 처치율이 **3.3 /s로 떨어진다** — 그 경우 §4.2의 정상상태가
상한 60에 더 오래 붙어 체감 난이도가 올라간다. 이것은 의도된 숙련 보상이다.

이 가정이 틀리면 §4.2 표 전체가 틀린다. **G2 재측정의 1순위 항목**이다.

### 4.2 `BIGWAVE` 스폰 규칙과 검산 (3600 tick)

진입 시 `SURGE` 이월 잔존을 12로 가정한다 `[TARGET]`.

#### 4.2.1 런타임 규칙 (전 페이즈 공통)

시뮬레이션은 분수 개체를 만들지 않는다. 대기열은 **개체 템플릿의 FIFO 큐**이며 투입 수는
항상 정수다. 이 블록이 스폰 공급의 **유일한 실행 규칙**이고, §3의 지연 규칙과 §1.6의
전이 정책이 모두 이것을 가리킨다.

```
// 타입
//   EnemyTemplate = { archetype: string, hp: number }
//   spawnQueue    : EnemyTemplate[]      // 정수 카운터가 아니다

// --- 매 스폰 tick ----------------------------------------------------------
// 1. 이번 tick의 신규 공급을 템플릿으로 실체화한다.
//    구간 규칙(§4.2.2)은 "개수"만 정하고, 아키타입 구성은 페이즈 믹스가 정한다.
offeredCount     = phaseSupplyCount()                    // 정수 (§4.2.2)
offeredTemplates = materialize(offeredCount, phaseArchetypeMix())

// 2. 신규 공급은 큐 뒤에 붙는다 → 대기분이 항상 앞선다 (FIFO)
spawnQueue.push(...offeredTemplates)

// 3. 빈 슬롯만큼 큐 앞에서 꺼내 스폰한다
freeSlots = max(0, CONCURRENT_CAP - aliveCount)          // 정수, ≥0 (이월로 음수 가능 → 클램프)
admitted  = spawnQueue.splice(0, freeSlots)              // EnemyTemplate[]
for (const t of admitted) world.spawn(t)                 // 신규 entityId 발급
aliveCount += admitted.length

// 4. 지표/임계는 큐 길이로 읽는다
if (spawnQueue.length > SPAWN_BACKLOG_THRESHOLD /* 40 */) emit("SPAWN_BACKLOG_SATURATED")

// 처치는 개별 적의 HP 소진 이벤트로만 발생한다. 처치율은 설계 기대값이지
// 런타임 감산 규칙이 아니다.
```

- `CONCURRENT_CAP` = 페이즈별 **총 생존 개체** 상한(§3). 스폰 허가량이 아니다.
- **대기열은 드롭되지 않고 우선 소비된다.** `push` 후 `splice(0, …)`이므로 먼저 들어온
  템플릿이 먼저 나간다. §1.6이 이월 템플릿을 큐 앞에 적재하는 이유가 이것이다.
- `aliveCount + admitted.length ≤ CONCURRENT_CAP`이 정의상 성립한다 —
  `splice(0, freeSlots)`는 `freeSlots`개를 넘겨 꺼낼 수 없다. **상한 초과 tick은 존재할 수 없다.**
- **템플릿이 `hp`를 싣는 이유:** 이월 개체의 누적 피해를 보존하기 위함이다. 정수 카운터로는
  이 정보가 소실되어 반쯤 깎아둔 `guardian`이 만피로 부활한다.
- 신규 공급 템플릿의 `hp`는 아키타입 최대 HP다.
- **처치율 0.070/tick은 설계 검산용 기대값이다.** 런타임은 이 값을 어디에도 곱하지 않는다.
- 검산 표(§4.2.3)는 기대값을 `floor`로 이산화한 **예상 궤적**이며, 실제 런은 표본마다
  다르다. 표는 상한 준수를 증명하는 용도이지 재현 대상이 아니다.

#### 4.2.2 구간 설계

| 구간 | tick 범위 | 공급 규칙 | 스폰 간격 | 의도 |
|---|---|---|---|---|
| A 급증 | 0–134 | 고정 배치 18 | 45 | 3배치로 상한까지 채움 |
| B 유지 | 135–2699 | **보충 누산기** (아래) | 45 | 상한에 고정 |
| C 감쇠 | 2700–3149 | **보충 누산기** | 45 | 유지 지속 |
| D 소탕 | 3150–3599 | 공급 정지 | — | 잔존 정리 기회 |

**보충 누산기 (구간 B·C의 공급 규칙)**

```
BIGWAVE_REFILL_RATE = 0.070   // /tick — 설계 기대 처치율과 동일하게 정의

// phaseSupplyCount() 의 구간 B·C 구현
refillAccum += BIGWAVE_REFILL_RATE * ticksSinceLastSpawn   // 45 tick당 +3.15
offeredCount = floor(refillAccum)                          // 정수 3 또는 4
refillAccum -= offeredCount
return offeredCount
// 템플릿 실체화와 큐 투입은 §4.2.1 공통 규칙이 소유한다. 여기서 재정의하지 않는다.
```

구간 A는 `phaseSupplyCount()`가 상수 18을, 구간 D는 0을 반환한다.

**고정 배치 4를 쓰지 않는 이유:** 45 tick당 기대 처치는 3.15명이다. 매 간격 4를 제시하면
간격당 잉여 0.85가 쌓여 구간 B의 57간격 동안 **≈48**이 누적된다. 이는
`SPAWN_BACKLOG_SATURATED`(40)를 **정상 플레이 중에** 넘긴다 — 경보가 상시 울리면 진단
지표로서 죽는다. 공급률을 기대 처치율과 **같은 값으로 정의**하면 정상 플레이의 백로그는
0 근처에 머물고, 경보는 실제 처치율 미달에만 반응한다.

**백로그의 의미 정의:** `backlog`는 "설계가 의도한 밀도를 플레이어의 실제 처치 속도가
따라오지 못한 누적량"이다. 공급률이 기대 처치율과 같으므로:

| 플레이어 처치율 | 생존 수 | `admitted` | 백로그 | 해석 |
|---|---|---|---|---|
| = 4.2 /s (기대) | 상한 근처 고정 | = `offered` | ≈0 | 설계대로 |
| < 4.2 /s | 상한에 붙어 포화 | < `offered` | 증가 → 경보 | 밀도 과다 또는 딜 부족 |
| > 4.2 /s | 상한 미달 | = `offered` | 0 | 숙련 보상 — 밀도가 내려감 |

#### 4.2.3 상한 준수 검산 (시뮬레이션 생성 궤적)

아래 표는 손으로 쓴 것이 아니라 §4.2.1 의사코드를 그대로 실행한 결정론 시뮬레이션의
출력이다. 전제:

| 항목 | 값 |
|---|---|
| 이벤트 순서 | 스폰 → 이후 45 tick 동안 처치 |
| `refillAccum` 초기값 | 0.0 (구간 B 진입 시) |
| `killAccum` 초기값 | 0.0 (tick 0) |
| 처치 이산화 | `killAccum += 3.15; kills = floor(killAccum)` |
| 진입 생존 | 12 (`SURGE` 이월) |

**전체 결과:** 80간격, 상한 위반 **0건**, `max(투입 후)` = **60**, `max(backlog)` = **0**,
총 투입 265, 총 처치 252, `FINALE` 이월 **25**.

**첫 `offered = 4`는 간격 10 (tick 405)이다.** 누산기가 0에서 시작하므로 구간 B는 3을 여섯
번 낸 뒤에야 4를 낸다(0.15씩 누적해 1.0을 넘기까지 7간격). 간격 7의 `4`는 공급이 아니라
**처치** 열이다 — 두 누산기의 위상이 다르기 때문이며, 이것이 손계산으로는 맞출 수 없는
지점이다.

**구간 B 공급 분포:** 57간격 중 `offered=3`이 49회, `offered=4`가 8회. 평균 3.14.

**상한 준수:** `admitted ≤ freeSlots = 60 − aliveCount`이므로 `투입 후 ≤ 60`이 정의상
성립한다. 시뮬레이션 80간격 전체에서 위반 0건, 최대 60.

**백로그 0:** 명목 궤적에서 `freeSlots ≥ offered`가 항상 성립하므로 `admitted = requested`,
즉 백로그는 전 구간 0이다. 따라서 `SPAWN_BACKLOG_SATURATED`(40)는 **설계 이탈에만**
반응한다. 실제 처치율이 기대의 70%(2.94 /s)로 떨어지면 간격당 잉여 ≈0.95가 쌓여 약
42간격(1890 tick) 만에 경보가 뜬다 — `BIGWAVE` 중반이며, 그 시점의 경보는 정확히
"이 플레이어에게 이 밀도는 과하다"를 뜻한다.

**구간 D 종료 생존:** 10간격 동안 32명 처치, 57 − 32 = **25명**이 `BIGWAVE` 종료 시점에
살아 있다. 이 25는 그대로 `FINALE`에 들어가지 않는다 — §1.6 전이 정책이 대기열 16 +
보스 부채 +18%로 환산하며, `FINALE` 진입 생존은 **8**이다.
구간 D에서 스폰을 끊는 이유는 플레이어에게 정리 기회를 주기 위함이며, 정리하지 못한
25체는 대기열과 부채라는 **유한한 처벌**로 보스전에 반영된다.

**재현:** 이 표는 §4.2.1 의사코드 + 위 전제로 재생성 가능해야 한다. 픽스처
`enc-bigwave-cap`(§7)이 같은 불변식(위반 0, 최대 60, 백로그 0)을 단언한다.

### 4.4 카메라 경계 읽기의 결정론 예외

"화면 밖 피해 금지"는 시뮬레이션이 카메라 상태를 읽는다는 뜻이며, 이는 렌더러 → 시뮬레이션
방향 의존이라 기본 계약(`렌더러는 스냅샷을 읽기만 한다`)과 충돌한다.

**해결:** 카메라 프러스텀을 렌더러에서 읽지 않는다. 대신 시뮬레이션이 **결정론적 가시
반경** `VISIBILITY_RADIUS = 3000`을 소유한다 `[TARGET]`. 런타임에 카메라를 조회하지 않는다.

**3000의 근거:** `camera-vfx-direction.md#2.2`가 렌더러 좌표계에서 실측했다. 렌더러는
게임플레이 24000 × 12000을 28 × 28 월드 평면에 **이방적으로**(z/x = 2.0) 사상하며, 줌
clamp 상한 41.58에서 portrait 390×844 기준 달성 가능한 최대 게임플레이 반경이 **3003**이다.
landscape는 4001까지 가능하지만 portrait가 landscape lock 실패 시의 폴백이므로 좁은 쪽을
계약값으로 삼는다.

초기 안이었던 9000은 월드 z반경 21.0에 해당해 평면 절반 14를 넘으며 **구현 불가능**이었다.
실제 카메라가 3000보다 좁게 보이면 그것은 카메라 스펙 위반이며 카메라 쪽을 고친다.

## 8. 난이도 검증 방법

완주 시간은 난이도의 대리 지표로 쓰지 않는다. **관측된 결정**을 센다.

| 지표 | 계측 방법 | 건강 범위 `[TARGET]` |
|---|---|---|
| 대시 회피 성공률 | `DASH_IFRAME_END.negatedHits > 0` 비율 | 0.45–0.75 |
| 콤보 완주율 | `COMBO_DROPPED{CHAIN_COMPLETED}` ÷ 전체 드롭 | ≥0.50 |
| 콤보 중단 사유 분포 | `COMBO_DROPPED.reason` 히스토그램 | `STAGGERED` ≤0.30 |
| 광역기 의존도 | `aoe-burst` 처치 ÷ 총 처치, 페이즈별 | `BIGWAVE`에서 0.30–0.55 |
| 예고 인지율 | 예고 방출 후 60 tick 내 이동/대시 발생률 | ≥0.70 |
| 무피해 패턴 회피율 | 패턴별 (회피 성공 ÷ 노출) | 패턴당 ≥0.40 |
| 스폰 백로그 포화 | `SPAWN_BACKLOG_SATURATED` 발생률 | ≤0.10 |
| 강제 종막 발생률 | `FINALE_OVERTIME` ÷ 총 런 | ≤0.15 |

**해석 규칙:** 완주 시간이 밴드 안이어도 대시 회피 성공률이 0.45 미만이면 패턴이 너무
빠르거나 예고가 안 읽힌다는 뜻이다. 시간만 보고 통과시키지 않는다.

이 지표는 전부 §7 픽스처의 스크립트 실행으로 **재현성만** 확인할 수 있다. 실제 난이도
판정은 사람 세션이 필요하며, 스크립트 출력은 사람 증거를 대체하지 않는다.
